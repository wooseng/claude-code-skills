# API 设计指南

## 基本原则
- 使用时的清晰性是你最重要的目标
- 清晰比简短更重要
- 为每个声明都写文档注释

## 命名
- 包含所有必要的词以避免歧义。在代码中使用名称时，要确保阅读者能够理解其含义
- 省略不必要的词。名称中的每个词都应该在使用场景中传达重要信息
- 根据角色来命名变量、参数和关联类型，而不是类型约束
- 补充弱类型信息以明确参数的角色
- 优先使用能在使用时形成语法正确的英语短语的方法和函数名称
- 工厂方法的名称应以 “make” 开头， 例如 `x.makeIterator()`
- 初始化器和工厂方法调用的第一个参数不应该与基本名称形成短语， 例如 `x.makeWidget(cogCount: 47)`
- 根据副作用来命名函数和方法，
  - 没有副作用的应该读起来像名词短语， 例如 `x.distance(to: y)`、`i.successor()`
  - 有副作用的应该读起来像祈使动词短语， 例如 `print(x)`、`x.sort()`、`x.append(y)`
  - 一致地命名可变/不可变方法对。 可变方法通常会有一个不可变的变体，具有相似的语义，但返回新值而不是就地更新实例。
    - 当操作自然地用动词描述时，使用动词的祈使语气来命名可变方法，并添加”ed”或”ing”后缀来命名其不可变的对应方法。
    - 当操作自然地用名词描述时，使用名词来命名不可变方法，并添加”form”前缀来命名其可变的对应方法。
- 不可变的布尔方法和属性的使用应该读起来像是对所作用对象的断言，当使用是不可变的时候，例如 `x.isEmpty`、`line1.intersects(line2)`
- 描述事物是什么的协议应该读起来像名词 (例如 `Collection`)
- 描述能力的协议应该使用后缀 able，ible，或 ing （例如 `Equatable`、`ProgressReporting`）
- 其他类型、属性、变量和常量的名称应该读起来像名词
- 如果一个更常见的词能同样好地传达含义，就避免使用晦涩的术语
- 如果使用了专业术语，请遵循其既定含义
- 避免缩写
- 拥抱先例，不要为了照顾完全的初学者而牺牲与现有文化的一致性

## 约定
- 给任何非 O(1) 的计算属性的复杂度写文档注释
- 优先使用方法和属性而不是自由函数
- 遵循大小写约定
- 方法可以共享基本名称

## 参数
- 选择能服务于文档注释的参数名称
- 利用默认参数来简化常见用法
- 优先将带有默认值的参数放在参数列表的末尾
- 如果你的 API 将在生产环境中运行，优先使用 #fileID

## 参数标签
- 当参数不能有效区分时省略所有标签，例如 `min(number1, number2)`、`zip(sequence1, sequence2)`
- 在执行值保留类型转换的初始化器中，省略第一个参数标签，例如 `Int64(someUInt32)`
- 当第一个参数构成介词短语的一部分时，给它一个参数标签。参数标签通常应该从介词开始， 例如 `x.removeBoxes(havingLength: 12)`
- 否则，如果第一个参数构成语法短语的一部分，则省略其标签，将任何前置词附加到基本名称上， 例如 `x.addSubview(y)`
- 为所有其他参数添加标签

## 特殊说明
- 标记元组成员并命名闭包参数，当它们出现在你的 API 中时
- 特别注意不受限制的多态（例如 `Any`、`AnyObject` 和不受限制的泛型参数），以避免在重载集合中出现歧义
